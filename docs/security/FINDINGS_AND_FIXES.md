# Crossing Protocol — Consolidated Findings and Fixes

Date compiled: **24 October 2026**; latest follow-up: **25 October 2026**.
Scope: every finding raised across the four internal review passes on this
repository — the original design review, the second design review, the
contract implementation review (including its three dated addenda), and the
cryptographic review — gathered into one place with a plain-language
explanation of each defect and exactly how it was fixed. This document does
not replace the four source reports it summarizes; it exists so a reader can
see the complete finding history without opening all of them. Each entry
below gives the plain explanation; the linked source report gives the
severity rationale, exact code paths, and regression test names.

This is still an internal development record, not an external audit report.
The fixed contracts have since been deployed to and exercised on Stellar
Testnet (see [deployments/](../../deployments/)); no Mainnet deployment or
independent third-party audit has occurred as of this date. **Every finding
listed below has a corresponding fix already
applied in this repository** — there are no open findings; remaining
unfinished work is tracked separately as release-acceptance gates (see
[DESIGN_AUDIT.md §5](DESIGN_AUDIT.md#5-open-implementation-and-deployment-gates))
and disclosed product trade-offs (see
[DESIGN_AUDIT.md §6](DESIGN_AUDIT.md#6-explicit-residual-risks-and-chosen-product-tradeoffs)),
neither of which are "bugs" in the sense this document covers.

Current test evidence referenced throughout: **60 integration tests** against
compiled WASM, **9 shared unit tests**, **50 design-model tests**, **15 tooling
tests** for coverage and WASM build identity, a **36-case independent commitment
matrix**, and **48 independently generated clearing vectors**. See
[TESTING.md](../TESTING.md) for how these are run and measured.

## How to read this report

- **Phase** groups findings by which review pass raised them, in
  chronological order.
- **Severity** is carried over unchanged from the source report.
- **What was wrong** explains the defect in plain terms: what a user,
  bidder, issuer, or attacker could actually do or observe.
- **How it was fixed** explains the correction in plain terms and names the
  regression test(s) that now lock the corrected behavior in place.

## Phase 1 — Original design review (first pass)

Source: [DESIGN_AUDIT.md §2](DESIGN_AUDIT.md#2-first-review-findings-and-corrections).
These findings were raised against the original specification, before any
contract code existed, and are all corrected in the architecture that the
contracts were then built from.

| ID | Severity | What was wrong | How it was fixed |
|---|---|---|---|
| D-01 | Critical | A Buyback auction summed up what bidders individually offered to be paid, instead of paying every accepted bidder the single final clearing price. Because the final price is set by re-pricing winners upward or downward, this could make the auction promise more than its budget actually covers. | The accepted quantity is now capped by `floor(budget × scale / price)` applied to the whole accepted group, and the quote amount owed is always floored at the uniform price, so the total paid out can never exceed the budget. Covered by sparse-gap and repricing tests plus the independent reference model. |
| D-02 | Critical | The issuer could withdraw sale proceeds before a later winner revoked their bid or failed to deliver, potentially leaving the pool short when that bidder needed a refund. | Every reversible trade now keeps its own reserve set aside until it is no longer reversible: sale proceeds are only released after actual delivery, and buyback payments are reserved for the exact promised amount. Tested with issuer-first-withdrawal scenarios. |
| D-03 | High | The design assumed a revoked bidder could always receive an immediate token refund, but SAC assets can have transfer restrictions (freezes) that block a plain transfer. | Refunds are now recorded as an internal credit owned by that same bidder/asset pair rather than attempted as an immediate transfer; a failed withdrawal attempt leaves the credit intact for a later retry. Tested with frozen-refund and expiry scenarios. |
| D-04 | High | Checking whether winning bidders are still authorized to trade was treated as one snapshot, even though sweeping all winners can take multiple transactions — an early-checked winner could revoke in between. | The final close now re-checks authorization for every price-relevant bid atomically, including marginal bids whose fill rounds to zero, with a disclosed 16-bid cap so this is always one atomic step. Covered by model and compiled-WASM revocation-after-prepare tests. |
| D-05 | High | The original rules exempted sale investors from compliance checks and were unclear about which side of a trade actually supplies the RWA token. | Every bidder in both Sale and Buyback mode must now be authorized for both the RWA and quote asset. Tested with a sale-investor rejection case. |
| D-06 | High | Calling a token contract's `authorized` method was treated as proof the token is a genuine Stellar Asset Contract — but any arbitrary WASM contract can implement that method and lie, or implement a malicious transfer. | The protocol now verifies the token is a genuine built-in SAC via its executable identity, and excludes native XLM and custom tokens from V1. Tested against genuine, native, and fake tokens. |
| D-07 | High | "The issuer opens the auction" had no concrete, enforceable rule for who is actually allowed to create one. | Creation and funding both now require the caller to hold the current admin authority of the RWA's SAC, checked and signed for at both steps. Tested against wrong, missing, mutated, and transferred admin authority. |
| D-08 | High | Contract deployment and initialization could race, or assumed an escrow contract could receive an AUTH_REQUIRED asset before its address was even authorized to hold it. | Deployment now uses a deterministic constructor address, a dormant "created but not funded" state, explicit SAC authorization, then a separate one-time funding step. Tested with real bootstrap pin failures, same-salt rollback/retry, double-construction rejection, and unfunded expiry. |
| D-09 | High | A sealed bid's commitment was just `hash(price, amount, salt)` — an ambiguous encoding with no binding to the bidder, network, auction, or deposit, so a commitment could potentially be replayed or misapplied. | Commitments are now a canonical, typed XDR structure binding a domain tag, network ID, auction address, owner, nonce, configuration hash, and deposit amount. Verified byte-for-byte against an independently written encoder across all 22 configuration fields and all 10 commitment components, plus runtime mutation/copy/replay tests. |
| D-10 | High | There was no complete, exactly-once rule for what happens to collateral behind a bid that is never revealed, or to excess collateral beyond what a reveal actually needs. | Every deposit is tracked to exactly one disposition: a reveal slot is consumed at commit time, excess collateral is held until resolution, and refunds always return the original asset. Tested for sealed excess, non-reveal, and replay cases. |
| D-11 | High | The clearing algorithm was described as "bounded by revocations" without a concrete, provably-terminating work measure, risking an auction that could restart indefinitely. | Clearing now uses explicit epoch resets, complete running totals, permanent exclusion of resolved bids, and a finite number of passes with real deadlines. A worst case of 4,096 price ticks and all 16 possible exclusions now provably finishes within 2,200 bounded calls. |
| D-12 | High | Multiplying large `i128` quantities, accumulating running totals, and rounding up before dividing could overflow before the division ever happened. | All such arithmetic now uses a wider intermediate type, checked casts and sums, and correct quotient/remainder-based rounding. Covered by overflow and maximum-`i128` reference vectors. |
| D-13 | High | The accounting model added token and stablecoin amounts together and assumed they must always balance, which mixes incompatible units and ignores unsolicited transfers sent to the contract. | Each asset now has its own separate liability ledger (pending escrow, reserved amounts, credits); unsolicited surplus is never silently treated as issuer revenue. Tested with generated lifecycle and "someone sent stray tokens" cases. |
| D-14 | High | The design promised "no settlement risk" unconditionally, but a token's admin can freeze or claw back funds already escrowed in the contract — a promise the contract cannot actually keep. | The documentation now states this external risk explicitly rather than denying it; the contract detects a resulting shortfall and suspends further outflows of that asset until it is externally replenished, rather than paying out insolvently. Tested against genuine SAC clawback and suspension/replenishment. |
| D-15 | High | An auction with an indefinite closing period or bidders who never claim their funds had no terminal path, risking assets stranded forever. | Closing and delivery now have separate explicit deadlines; cancellation and bid expiry are permissionless (anyone can trigger them) and always preserve the underlying credits so funds are never lost, only delayed. Tested at the exact deadline boundaries. |
| D-16 | Medium | For an undersubscribed sale, cumulative demand was being assigned as if it were each tick's own marginal quantity, which could double-count demand; the reserve price and a separate `limit_price` field could also contradict each other. | Removed the redundant field; an undersubscribed sale now fills the full ratio at the reserve price. Tested with a dedicated partial-sale regression. |
| D-17 | Medium | The pro-rata fill ratio was applied to a bidder's *requested* volume as if that were their actual allocation, even though integer rounding can make the real fill smaller. | The actual filled quantity is now computed after rounding and after filtering out any fill that rounds to zero, before checking it against the bidder's stated minimum. Tested for actual-vs-nominal minimum and dust cases. |
| D-18 | Medium | The meaning of a bid's "amount" field changed between Sale and Buyback mode, and price scale, asset decimal places, and which side's rounding direction applies were never pinned down precisely. | A bid amount is now always defined as an RWA quantity; the quote asset is fixed at 7 decimal places; deposits and payment rounding are asymmetric by design (always in the protocol's favor) and documented exactly. Tested with fixed-point and generated-book cases. |
| D-19 | Medium | TTL (time-to-live) handling was described only as "an absolute ledger promise," with no stated maximum horizon, no distinction between relative and absolute semantics, and no maintenance or restoration policy. | TTL is now defined precisely as excluding the current ledger, with a forced initial instance/code retention horizon and bounded, permissionless maintenance calls to renew it. Tested with exact live-until assertions and an aged-shared-code scenario (this is also where contract-review findings C-07/C-08 below apply). |
| D-20 | Medium | Using global growing maps/vectors for bidders and an unspecified winner index risked exceeding Soroban's per-entry storage or per-transaction size limits as an auction grew. | Storage now uses separate persistent entries per bid, dense sequential bid IDs, bounded counters, and paginated ID listing instead of one growing collection. |
| D-21 | High | The price registry's provenance was underspecified: if a caller could supply its own metadata when publishing a price, that publication could be forged. | The registry now pins the exact factory and auction-template executable hashes, pulls configuration and results directly rather than accepting caller-supplied data, and cross-checks registration before accepting a publication. Tested against fake publications and unregistered clone contracts. |
| D-22 | Medium | Prices were keyed only by the RWA asset, ignoring which quote asset they were priced against, and a late publication could silently replace a newer, already-published price. | Prices are now keyed by the full asset pair and ordered by source ledger (with raw contract ID as a tie-break), with source time kept separate from publication time. Tested for delayed/duplicate records, same-ledger ties in both possible orders, and zero-execution records. |
| D-23 | Medium | If the inline call to publish a result to the registry failed for any reason, the whole closing transaction could revert, blocking every bidder's claim. | Publication is now a separate, independently retriable step from immutable already-settled state, so an injected publication failure does not block any bidder's delivery or claim. |
| D-24 | High | The registry's *allocated* clearing price/volume could be mistaken for genuinely *executed* trade data, even after post-clearing refunds or revocations reduced what was actually delivered. | The registry now separates the allocated clearing record from the actual execution record, explicitly records a zero-execution case when nothing was ultimately delivered, and documents that raw registry data must never be used as automatic collateral-pricing input without a curated layer on top. |
| D-25 | Medium | The word "sealed" overstated the actual confidentiality guarantee (deposits and timing remain public), and a "SEP-compatible" oracle claim was made without actually implementing the SEP-40 interface. | Documentation now states the metadata/withholding limits explicitly and describes the optional bounded non-reveal penalty precisely; the implemented oracle adapter is documented as a deliberately *partial* raw SEP-40 surface, not a full implementation. |
| D-26 | High | Claim effects and the two-leg nature of a Buyback settlement (pay quote, deliver RWA) had no precisely specified atomic/rollback behavior if one leg failed. | Delivery must now complete before earned proceeds are released, recipients are fixed, and every outcome has a typed effect with defined rollback. Tested with a genuine SAC second-leg failure that rolls back the first leg and all accounting, followed by a successful retry. |

## Phase 2 — Second design review

Source: [DESIGN_AUDIT.md §3](DESIGN_AUDIT.md#3-second-review-findings-and-corrections).
A follow-up pass specifically checking for implementation details missing
from the first, now-corrected design.

| ID | Severity | What was wrong | How it was fixed |
|---|---|---|---|
| S-01 | High | A Buyback auction's payout recipient could be set equal to the escrow contract itself (or the factory/registry). A "delivery" to itself would count as complete while the RWA it acquired stayed stuck as surplus the contract couldn't use. | The recipient is now rejected if it equals the auction, factory, or registry contract, or any bidder address, and the actual deployed address is re-verified at funding time. |
| S-02 | High | A budget and a low price could each individually fit within `i128` range, yet the maximum quantity they imply together could overflow — meaning a fully funded auction could fail on every attempt to clear. | The maximum affordable quantity is now explicitly bounded at configuration-validation time, before the auction can even be created. Tested with an overflow-capacity case and maximum-`i128` books. |
| S-03 | Medium | If every marginal (last-tick) fill individually rounded down to zero, describing "the price" as if it corresponded to one actually-delivered bid became misleading. | The nominal aggregate marginal price is now explicitly distinguished from the actual fill/payment amounts, and both are reported separately. (Nominal price is reported before indivisible per-bid rounding is applied.) |
| S-04 | High | Fixed maximum entry counts (like the 16-bid cap) do not by themselves bound the *serialized byte size* of a response — returning full pages of configs or bids could still exceed Soroban's response-size limits. | Public getters now return bounded ID/address lists and single-record lookups instead of full pages of structured data, and byte sizes (key, entry, return, event) are explicitly measured and asserted in tests rather than assumed. |
| S-05 | High | "Pin the factory/registry hashes to each other" sounded simple but left the actual circular-dependency problem unspecified: the registry needs the factory's future address, and the factory needs the registry's real address. | A precise bootstrap sequence is now specified: hash arguments, a precomputed factory address, mutual hash bindings checked at construction, and a salt preimage that includes all of this. Tested for all four possible pin mismatches, atomic rollback/retry on failure, and salt namespace isolation. |
| S-06 | Medium | A stage that is merely implied by the current time (e.g. "past the close deadline") could be mistaken for a stage that has actually been recorded as settled, and it wasn't explicit that each initialization step can only happen exactly once. | The persisted stage, the time-derived bidding-phase flag, and expiry flags are now three distinct, separately checked things; each one-time initialization step has an explicit guard against being repeated. |
| S-07 | Medium | Public methods lacked an exact specification of bounded results, which fields persist in storage, the exact balance/liability deltas each call produces, and which authorizations each call requires — leaving room for an inconsistent independent reimplementation. | The architecture and [API reference](../reference/CONTRACT_API.md) now match the implemented wire types, storage layout, outcome records, and authorization trees exactly, with tests covering the current wire format and authorization scope of each call. |
| S-08 | Medium | A generic "fail closed on error" rule risked either permanently excluding a bidder after a merely transient query/restore error, or rolling back progress that an exclusion step had already correctly made. | The logic now distinguishes three outcomes explicitly: a definite "not authorized," a transient error (retry later, no state change), and a successful `Excluded` state change that is not rolled back. Tested with fault-injected SAC/host errors. |
| S-09 | Medium | Describing clearing cost only as "O(ticks)" hid the actual resource and capacity trade-offs of a maximum-size, maximum-repeat clearing run. | Documentation now discloses the actual complexity (O(bids) per validation pass), the 16-slot baseline capacity, and the measured maximum of 2,227 continuation calls for the worst case — with the explicit caveat that this is not a throughput or network-fee guarantee without further benchmarking. |

## Phase 3 — Contract implementation review

Source: [CONTRACT_REVIEW.md](CONTRACT_REVIEW.md). Raised once the design
above was actually implemented in Rust and compiled to WASM, across the
original pass and three dated addenda.

| ID | Severity | What was wrong | How it was fixed |
|---|---|---|---|
| C-01 | — | A finalizer handling the full 32-bid design exceeded the SDK's default per-transaction footprint limit: it needed 103 ledger entries against a limit of 100 in the tested layout. CPU usage alone looking fine did not mean the transaction would actually execute. | The hard bid-count cap was lowered to 16 (including non-reveals), and every model, test vector, and architecture reference was updated to match. The maximum-winner compiled-WASM test now passes under the real default resource limiter with explicit CPU/memory/footprint assertions. |
| C-02 | — | Token-transfer errors from the underlying SAC were passed through the protocol's own error type in a way that could mislabel a genuine SAC failure as an unrelated protocol error, and there was no proof that a two-leg transfer failure actually rolled back cleanly. | Failed token transfers are now normalized to one specific `Error::Transfer` variant and the failure propagates from the root call. Tested with a genuine SAC second-leg balance-overflow failure that rolls back the first transfer and all accounting, followed by a successful retry once capacity is restored. |
| C-03 | — | The SDK's native-test build converted `Option<custom type>` differently than the WASM guest build, so the same persisted data didn't compile consistently across the two. | Explicit wrapper enums (`CandidateValue`, `ReasonValue`, `ResolutionValue`) are used in both builds instead of relying on the ambiguous conversion. This was a build-compatibility defect, not a demonstrated loss-of-funds exploit. |
| C-04 | — | There was no running total of cumulative successful withdrawals, and no direct public getters for several already-published design fields (tick totals, cancellation reason, pair history count). | These are now tracked atomically alongside credits/balances/liabilities and exposed as direct getters. The sale demonstration exercises withdrawing both bidder refunds and issuer proceeds and reconciling the resulting token balances. |
| C-05 | Medium | Configuration validation accepted native XLM as the *quote* asset, because native XLM also presents an "executable identity" and 7 decimal places identical to a genuine SAC — violating the rule that only issued assets are allowed. | The quote asset must now pass the same issued-SAC admin-interface check as the RWA asset. A regression confirms the old code accepted native XLM on the quote side and the fix rejects it on both sides. |
| C-06 | — | Most of the economic correctness evidence ran only against the Python/JS reference models, not against the actual deployed guest WASM — leaving limited runtime evidence for commitment mutation, overlapping expiry, and delayed registry publication. | Added 48 independently generated clearing fixtures run against the compiled WASM itself, plus commitment mutation/copy/replay/underfunding tests, overlapping-expiry-batch tests, and source-ordered/zero-execution registry tests. |
| C-07 | Medium | A fresh auction reusing an older shared WASM code entry could inherit that code's existing TTL, which could already be shorter than the new auction's own required delivery/recovery horizon — observed concretely as an instance TTL of 518,400 ledgers against a code TTL of only 300,000, for an auction needing 470,960. | Both the new instance's storage *and* the shared code entry are now force-extended to the full required financial horizon at construction time (`threshold = extend_to`), with normal half-horizon rolling renewal afterward. No funds were ever at risk; the defect would only have created an unexpected restoration requirement before delivery could occur. |
| C-08 | Low | The TTL calculation added one extra ledger on top of a horizon that the SDK already defines inclusively, causing the exact supported maximum horizon to be wrongly rejected. | Removed the extra ledger; a regression now accepts exactly the maximum allowed horizon and rejects one ledger beyond it. A scheduling-correctness defect with no financial exposure. |
| C-09 | — | Factory test coverage didn't directly establish every bootstrap pin-mismatch failure, signed-argument binding, admin changes between creation attempts, namespace isolation between issuers, or rollback behavior after a successful child deployment followed by a later factory-side error. | Added direct tests for all four possible pin mismatches with same-salt retry, rejection of re-invoking an already-constructed contract, exact authorization/config/salt mismatches, transferred-admin rejection, salt namespace separation by issuer/network/factory, and rollback after an injected post-deployment counter fault (a deliberately injected test condition, not a realistically reachable one on its own). |
| C-10 | Medium | A marginal bid whose actual fill or payment rounds to zero can still influence where the uniform clearing price lands, but the original sweep and the one-shot finalizer skipped authorization checks for such bids — so a revoked zero-fill bid could silently reprice the winners around it, or block an otherwise deliverable book from clearing at all. | Both the batched sweep and the atomic finalizer now check authorization for every revealed, non-excluded bid at or better than the candidate price — including zero-fill ones. A definite revocation subtracts its quantity and restarts clearing; a transient query failure still aborts safely rather than guessing. Tested in both Sale and Buyback mode, including a zero-payment Buyback bid that becomes deliverable once excluded. |
| C-11 | — | *(Scope addition, not a defect in prior code.)* The fourth deployable contract, `OracleAdapter`, needed its own review before being added: does it hold funds, can it change auction accounting, does it have a freshness/manipulation policy? | Confirmed it is read-only (no funds, no accounting authority), exposes only `base`/`decimals`/`resolution`/`lastprice` (a deliberately partial SEP-40 surface — `assets`/`price`/`prices` are intentionally absent), and pins its registry address once at construction with no re-pinning needed afterward since it never receives a caller-supplied registry address to re-verify. Covered by read, bootstrap, source-time, and retention tests; strengthened further by C-15/C-16 below. |
| C-12 | — | *(Scope addition.)* The new optional non-reveal penalty needed review for its own correctness: does it only apply where intended, and does it preserve conservation of funds? | Confirmed it is zero by default, capped at 50%, forced to zero in Open-bid mode (where there is no reveal step to skip), and only applies to the specific `NonReveal` resolution reason on a cleared auction — every other refund path (cancellation, expiry, revocation) is unaffected. The penalty amount is credited to the issuer through the same internal credit mechanism used elsewhere, so total asset conservation holds by construction. *(This finding's precise timing boundary was later found to be bypassable — see C-19.)* |
| C-13 | Low | The internal `store`/`leave` storage helpers each independently re-read and re-deserialized the full 22-field `Config` from instance storage on every call, even when every caller already had a `Config` value in hand from earlier in the same invocation — and a single bid placement could trigger this redundant read three or four times over. | Both helpers now take the caller's already-loaded `&Config` directly instead of re-reading storage. This is a pure performance refactor with identical TTL arithmetic, storage keys, and error conditions — re-verified against the full test suite and coverage gate. It matters more than a typical micro-optimization because this contract already runs close to Soroban's per-transaction resource ceiling (the same ceiling that caps `MAX_BIDS` at 16), so removing wasted CPU from the hottest paths directly protects that headroom. |
| C-14 | Medium | In Sealed Sale mode, the *total collateral* across all bids could fit within `i128` range while the *sum of hidden quantities* they would reveal to overflowed it — meaning an otherwise valid, fully funded reveal could fail outright, and could then incorrectly incur the non-reveal penalty for a bidder who did nothing wrong. | Before accepting any collateral, the maximum quantity that collateral could possibly reveal (`floor(total_admitted_deposits × scale / min_price)`, computed in a wider integer type) is now bounded to fit `i128` up front. Since every valid revealed quantity is bounded by its own deposit and price, the total can never overflow regardless of reveal order. Tested: the old code accepted an unsafe second commitment that the fix now rejects before any transfer, nonce, or slot write occurs; the same nonce can then retry with supported collateral; and near-limit quantities are tested in both reveal orders. |
| C-15 | Low | The oracle adapter had no way to renew its own storage TTL after deployment, and used a rolling-extension threshold at construction that could let its *shared code entry* expire earlier than its own instance if that code was reused from an older deployment. | Both instance and shared code are now force-extended to the full supported retention target at construction, and a new permissionless `maintain()` entrypoint allows anyone to renew them afterward. Tested with an artificially aged shared-code scenario and both native and WASM execution modes, confirming the actual TTLs and that bindings (registry pin, base asset) never change. |
| C-16 | Low | The oracle adapter's constructor accepted native XLM as a valid base asset, even though this release's auctions already exclude native XLM entirely — leaving a constructible adapter that pointed at an asset the rest of the protocol doesn't support. | Construction now requires a genuine 7-decimal issued SAC with a working admin interface, exactly like the auction's own asset checks. Tested: wrong registry pins, fake base assets, and a genuine native-XLM base all fail atomic deployment; retrying the same salt with a supported base then succeeds. |
| C-17 | Informational | A code comment describing the price registry's same-ledger tie-break rule (raw contract ID order) implied that routing publication through the factory made this ordering immune to being gamed — but an issuer can predict or grind for a favorable salt/address ahead of time. | The comment now states plainly that this is a deterministic but economically arbitrary tie-break with no independence or fairness guarantee. No behavior changed — this was a documentation-accuracy fix only. |
| C-18 | — | The custom coverage-gate checker (the tool that enforces the 95% line-coverage requirement on every contract) had its own defects: it accepted a source file with zero lines and no function map as "100% covered"; a later duplicate record for the same file could silently overwrite an earlier, correctly-undercovered one; a source file missing its production function map could still report a passing counter; and in "reuse" mode, a stale merged profile could be reused if the current run produced no fresh raw profiles. | The checker now requires positive integer counters bounded by the actual source size, rejects duplicate source records, requires a production function map for every source, and rejects invalid regions or LLVM-reported mismatches. It also clears prior reports before a fresh run and clears merged profiles before a reuse run. Nine dedicated tooling tests cover both correct acceptance and each of these rejection cases, plus isolated cleanup after a failed run. This affects the trustworthiness of the *test evidence itself*, not any deployed contract's actual behavior — the previously reported coverage numbers, once re-measured with the fixed checker, were confirmed accurate. |
| C-19 | Medium | **The non-reveal penalty (C-12) could be deterministically bypassed by timing.** The `resolve()` function checked the caller-supplied "expired" flag *before* checking whether a bid had simply never been revealed. This meant a sealed bidder who never revealed their bid could just let the delivery deadline pass without being resolved — instead of being resolved via the normal `claim_bid` path, it would then get swept up by the permissionless `expire_bid`/`expire_range` path, which reported the generic `DeliveryExpired` reason and silently skipped the penalty, refunding the full deposit regardless of who triggered the resolution or when. In other words, the best strategy for a bidder who regretted revealing was simply to wait — and this had already been written into both a test and the architecture document as if it were the *intended* behavior, which is exactly why a review that does not treat the existing tests and documentation as ground truth was necessary to catch it. | `resolve()` now classifies a never-revealed bid as `NonReveal` *before* checking the timing-derived `expired` flag, for any auction that actually reached the `Cleared` stage — so the penalty applies identically whether the bid is resolved before the delivery deadline via `claim_bid` or after it via `expire_bid`/`expire_range`. A `Cancelled` auction (one that never cleared, so no price was ever distorted by the withheld reveal) still takes precedence and still refunds in full — there is nothing to deter in that case. The test that had encoded the old, bypassable behavior as intended was corrected to assert the new precedence, and the architecture document's claim that "the penalty is not guaranteed to be collected" was removed. Total fund conservation was never affected by this defect — it only ever changed which refund *reason* and *split* applied, never whether `refund + issuer_credit == original_deposit`. |

## Phase 4 — Cryptographic review

Source: [CRYPTOGRAPHIC_REVIEW.md](CRYPTOGRAPHIC_REVIEW.md). This pass found
**no exploitable cryptographic defect** in the reviewed source. It closed
assurance gaps — places where a property was likely true but not yet
directly demonstrated — rather than fixing broken behavior.

| Finding | What the gap was | How it was closed |
|---|---|---|
| Thin vector coverage | A single fixed test vector did not, by itself, demonstrate correct encoding of every one of the 22 configuration fields or all 10 commitment components, nor several boundary cases (values crossing the 64-bit boundary, `i128::MAX`, both account-owner and contract-owner cases). | Added a 36-case matrix independently generated and cross-checked against a from-scratch XDR encoder (one that does not reuse any Stellar SDK or the protocol's own hashing helper), plus a Rust conformance test comparing production output against those same fixed hashes. The original single vector is kept alongside the new matrix, not replaced. |
| Mocked-only authorization | Tests using matched mock-authorization trees demonstrate that the *shape* of a required call tree is correct, but not that real Ed25519 signature verification, credential expiration/replay rejection, classic-account authentication, or authenticated-callback reentry actually work end to end. | Added four runtime regressions that submit genuine signed Soroban authorization entries (real Ed25519 keypairs, real classic account/trustline ledger entries, real signature-replay and reentry attempts) rather than mocks, plus two further classic-authority regressions covering a classic SAC admin and a 2-of-2 classic multisig account. |
| Configuration schema change vs. version number | Adding the `nonreveal_penalty_bps` field changed what gets hashed into the configuration digest, while the configuration's own declared schema version number stayed at `1` — raising the question of whether an old client payload could be silently misinterpreted. | Confirmed the SDK's decoding requires the exact current field set, so a payload built against the old schema fails to decode at all rather than silently hashing to something different; this is treated as a release-identity/compatibility requirement for client tooling, not a cryptographic defect, since nothing in the contract itself was shown to accept a mismatched or replayed configuration. |

## Phase 5 — 25 October 2026 evidence and model follow-up

An AI-assisted source, compiled-WASM, coverage, and read-only Testnet review
identified three evidence issues. The user authorized their correction after
the initial verification-only review. All production contract sources and all
four deployed WASM hashes remain unchanged; this is not an external audit
certification or a new deployment.

| ID | Severity | Finding | Correction and re-verification |
|---|---|---|---|
| CROSS-L01 | Low | The Python lifecycle model and several active summaries still waived a cleared non-reveal's penalty after delivery expiry, contradicting C-19's deployed policy. | Align reason precedence with the contract: cancellation, non-reveal, then delivery expiry. ## What remains after all of the above

Every finding above has a corresponding correction applied in the repository
and supporting verification described in its review record. Commit and publication
status are established by Git history rather than by this review record. What is
intentionally **not** claimed fixed, because it isn't something a
smart-contract fix can resolve by itself:

- **External asset-administrator powers** (freeze, clawback) on the
  underlying Stellar assets — the contract detects and safely suspends
  outflows if this happens, but cannot prevent it.
- **Network-level qualification**: wallet signing, transaction envelope
  submission, fee/footprint behavior on an actual deployed network, and
  independent third-party audit — tracked as the release-acceptance gates in
  [DESIGN_AUDIT.md §5](DESIGN_AUDIT.md#5-open-implementation-and-deployment-gates).
- **Disclosed product trade-offs** that are deliberate design choices, not
  defects: the 16-bid capacity ceiling, public deposit visibility even in
  "sealed" mode, no privileged rescue/upgrade path, and the fact that a raw
  on-chain clearing price does not by itself certify a fair or manipulation-free
  market. Listed in full in
  [DESIGN_AUDIT.md §6](DESIGN_AUDIT.md#6-explicit-residual-risks-and-chosen-product-tradeoffs).
